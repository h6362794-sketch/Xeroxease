Your task is to design and build a **production-grade, secure, premium, highly animated full-stack web application called "XeroxEase — Efficient Document Solutions."**

This is NOT a simple college CRUD project.

Treat XeroxEase as a real-world document-printing platform that can eventually serve hundreds or thousands of college students.

The application solves this problem:

Students, especially hostel students, often cannot reach a Xerox/printing center at the right time. XeroxEase allows them to upload documents remotely, configure printing requirements, make payment using a secure QR/scanner-based payment flow, track their order, and collect the completed documents.

# 12. AI DOCUMENT PAGE DETECTION

This is a core feature.

After the user uploads documents, the system should automatically analyze the uploaded documents and determine:

* Number of pages
* File type
* File size
* Processing status
* Any supported document metadata

For PDF files, page count should be determined using reliable server-side document processing.

For DOC/DOCX/PPT/PPTX files, use a reliable document-processing method capable of determining the printable page/slide count where technically possible.

The AI/document-processing layer should assist with document analysis but must NOT blindly invent page counts.

If page count cannot be reliably determined:

Display:

**"Page count could not be automatically determined. Please verify the document or allow an administrator to review it."**

The system should store:

* `pageCount`
* `pageCountSource`
* `analysisStatus`
* `analyzedAt`

Possible page-count sources:

* DOCUMENT_PARSER
* AI_ANALYSIS
* ADMIN_VERIFIED
* USER_CONFIRMED

The server must use the verified page count for pricing.

Users should be able to see the detected page count before submitting the final order.

Administrators should be able to review/correct page count when necessary.

Any manual correction must be recorded in the audit log.

* PAYMENT_UNDER_REVIEW
* PAYMENT_CONFIRMED
* PAYMENT_REJECTED
* PAYMENT_FAILED

* Reject payment
* Add verification notes
* View verification timestamp
* View verifying administrator

Students must never be able to mark their own payment as confirmed.

If a payment API/provider is added later, the architecture should allow integration without redesigning the order system.

# 85. IMPORTANT PAYMENT PRINCIPLE

**NEVER trust client-side payment status.**

The student can indicate that payment has been made, but only an authorized verification process can mark the payment as:

**PAYMENT_CONFIRMED**

The QR image itself is only a payment mechanism/display asset.

Do not falsely represent QR scanning as automatic payment verification unless an actual payment provider integration is implemented.

* Authorized administrator

# 88. IMPORTANT DATABASE PRINCIPLE

**NEVER trust IDs supplied by the client.**

Every resource must be checked against the authenticated user's permissions.

Supabase credentials must never be exposed to the browser except intentionally public client-side configuration such as the Supabase anon/public key, where appropriate.

# 92. FINAL OUTPUT REQUIREMENT

Build the actual working full-stack XeroxEase application.

Do not provide only static mockups.

Do not fake API responses in production code.

Do not hard-code authentication.

Do not hard-code order data.

Do not hard-code payment confirmation.

Do not store passwords as plaintext.

Do not expose uploaded files publicly.

Do not create public admin registration.

Do not trust client-side prices.

Do not trust client-side roles.

Do not trust client-side payment status.

Do not trust client-side page counts as the final pricing source.

Do not skip server-side authorization.

Do not claim "100% secure."

Instead, implement strong defense-in-depth security and clearly document deployment requirements.

The database must use **Supabase PostgreSQL** and be straightforward to configure using environment variables and Prisma migrations.

Online payment must use the **administrator-managed QR/scanner payment workflow** rather than the previously specified Razorpay workflow.

The application must automatically analyze uploaded documents and determine page counts wherever technically possible, with safe fallback and administrator verification when automatic detection is unreliable.

Students must be able to cancel eligible orders.

Administrators must be able to update order status.

Students must be able to submit ratings and feedback after successfully receiving/completing their orders.

The final result should feel like a premium production-ready document-printing platform created by an experienced product engineering team.
